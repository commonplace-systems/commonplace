## 2. The defect

`failed_enumeration_record/1` (~:309) sets `"commit_ids" => nil` for a document
whose commit enumeration failed. `commits_total/1` does
`Enum.flat_map(&(&1["commit_ids"] || []))` — **so `nil` becomes `[]` and that
document contributes ZERO to the denominator.**

⇒ **A document the sweep learned NOTHING about — not even how many commits it
has — cannot lower coverage. Failures remove themselves from the measure of
failure.**

⚠️ **And it is SELF-REINFORCING, which is what makes it worse than a plain
missing denominator: the more enumeration fails, the healthier coverage looks.**

The percentage currently means *"of the commits we could SEE, this fraction were
scanned"* — **a denominator built from what SURVIVED rather than what ARRIVED**,
which is the rule this scanner was explicitly built to honour and **the second
place it has failed it** (the first was counting attempts as verdicts, CX-1n8y).

**The mitigation that exists and must be KEPT:** these documents *are* counted
in `docs_fully_unscanned`, so the information is in the summary line. ⚠️ But
only a reader who knows to cross-check that field is protected, **and the
percentage is the thing people quote.**

## 3. The work — a decision, then the code

**Establish first, then choose:**

1. ⭐ **Can a commit COUNT be recovered for an enumeration-failed doc?** Is
   there a cheaper enumeration that yields a count even when the full list
   fails? **If yes, the denominator can simply be honest, and that is the best
   outcome.** Answer this with a measurement, not an assumption.
2. **If not, coverage cannot be a single percentage without lying.** Options,
   and any of them satisfies §1: report a range; refuse the percentage when any
   doc failed enumeration; or print it with an explicit *"+N docs of unknown
   size"* rider so the figure carries its own incompleteness.

⛔ **Say which you chose and why**, and what it costs a reader.
